# 03 ループ(L1〜L9、L4'、L5')全仕様

v3の点線(フィードバックループ)の全部。各ループに、**きっかけ・戻す先と中身・反復の上限・終了条件・上限を超えたときの返し方・費用・記録・フェーズ・完了の実測条件**を決める。上限と閾値の数値は**既定値**(設定で変更可)。評価セット(`06` 6節)で調整し、緩める場合は理由を記録して林さんに報告する。

## 0. ループの共通の仕組み

### 0.1 `LoopBudget`・`LoopCounter`と、頭打ちの定義

- 各ループは`LoopBudget(loopId, maxIterations, threshold, plateauDelta, onExceed=ESCALATE)`を持つ。回数と各回のスコアは`LoopCounter`としてプロジェクトに**保存**する(再起動しても数え直さない)。
- **止まる条件**は4つ: (a)成功(終了条件を満たす)、(b)上限回数、(c)頭打ち(スコアの改善が`plateauDelta`未満のまま2回続く)、(d)費用の上限線(`CostLedger`の金額・画像の回数・Codexのトークン数のどれか)。(b)(c)(d)のどれかで**自動では回さず、ユーザーに返す**(`ESCALATE`)。
- **スコア(各ループの「改善」を測る量)を、ループごとに固定する**(頭打ち判定が計算できるように):

| ループ | スコア(小さいほど良い/大きいほど良い) | `plateauDelta` |
|---|---|---|
| L2 | `coverageScore`(0〜1、大きいほど良い) | 0.05 |
| L3・L4 | 重み付きの`Issue`点数 = 10×(ERROR件数)+1×(WARN件数)(小さいほど良い) | 5 |
| L4' | 不足している空間(必要な床面積 − スロットの合計面積、セル数。小さいほど良い) | 全体の5% |
| L5・L5' | `matchScore`(0〜1、大きいほど良い) | 0.03 |
| L7 | `Deviation`の件数(小さいほど良い) | 1(直らなければ頭打ち) |
| L8 | 目標に対する実測の生産比(0〜1、大きいほど良い) | 0.05 |
| L1・L6 | (自動の反復が無い。回数のみ) | — |

### 0.2 ユーザーへの返し方(`LoopEscalationScreen`)

上限に達したとき、次を1つの画面で見せる: どのループか、何回試したか、各回のスコアと主な差分、今の最良の版、使った費用(金額・画像の回数・トークン)。選べるのは次の4つ(ここは利用者の判断が要る分かれ道なので、選択肢で聞く):
1. **続ける**(追加で`N`回)
2. **この結果で進む** — **ただし、受け入れ不可(`acceptable=false`)の`ERROR`が残っている場合は、この選択肢を出さない**(承認できないため)。受け入れ可能な問題は、`ACCEPTED_RISK`として記録して進める。
3. **前の段に戻る**(戻す先を選ぶ。`RouteChooserScreen`)
4. **中止**(プロジェクトは保存されたまま)

### 0.3 段の依存と「古くなった」印(`Invalidation`)

- 成果物の依存(上流 → 下流):
  ```
  ConceptBrief
   ├→ ConceptArt(画像) → StructureDescription ─┐
   ├→ ProcessGraph → CapacityReport ────────────┼→ ReconcileResult → ZoningPlan
   └→ (PowerPolicy)                             ┘        │
  ZoningPlan → 建屋ごとの画像3種 → 建屋の SemanticPlan(構造) → SemanticMap
   → モジュール配置・接続 → ExpandedPlan(経路) → 解析結果(PredictionReport) → 装飾 → LogisticsPlan
   → PlacementManifest → PREVIEW画像 → CritiqueReport
  ```
- ある成果物をやり直すと、**それに依存する成果物に「古い」印**を付ける。決定論の段は即座に再計算する。AIの段は、入力の資料(`Dossier`)のハッシュが変わっていなければ、前回の出力を再利用する(`StageMemo`)。変わっていれば、その段だけ再実行する。
- **画像の扱い**: 上流(`ConceptBrief`の外観に関わる項目、`ZoningPlan`など)が変わると、下流の画像は`stale=true`になるが、**自動では再生成しない**(画像は高価なため)。再生成は、L1・L2・L5'、またはユーザーの明示的な操作のときだけ。staleの画像は、Vision Reader・Architectの資料に使う前に、警告を出して、ユーザーに「使う/再生成」を確認する。
- これにより、L4'(建屋拡張)のように上流へ戻るループが、下流を壊さずに、必要な分だけやり直せる。

### 0.4 世界を書き換えるループの承認

- 施工前のループ(L1〜L6の大半)は、計画とプレビューだけを変えるので、世界は無変更。
- **建てた後**に世界を変えるやり直し(L6・L8の変更、建てた後の外観の直し)は、新旧の`ManifestDiff`から`MODIFY`ジョブを作り、**差分のホログラム(追加=緑、撤去=赤、変更=黄)と共にもう一度承認**を求める(D-3・D-14)。
- **`MODIFY`は、世界の現状が旧施工リストの期待(`expectedNow`)と一致する位置だけを変える**。一致しない位置(プレイヤーが置き換えた物)は`Conflict`として、触らずに記録し、実行後にユーザーへ返す(`01` 4.1節)。
- 例外: **L7の修復ジョブ**は、承認済みの施工リストをもう一度当てるだけなので、再承認は要らない(同じハッシュのもの)。

### 0.5 プレビュー撮影(v3の順序とゲーム内撮影の整合)

v3では、見た目の照合(Stage 3)が、承認(Stage 4)と施工(Stage 5)より前にある。しかし「ゲーム内の実物」を撮るには、建物が要る。これを次のように解決する:

- **`PREVIEW`撮影**(施工前): 施工リストを、**クライアント側だけ**で、本物のブロックモデルの見た目で不透明に描画(`HologramRenderer`の不透明モード)して、その場所の景色の中でスクリーンショットを撮る。**サーバーの世界は書き換えない**(D-1)。L5・L5'は、この撮影で回す。
- **`AS_BUILT`撮影**(施工後): 実際に建った世界を撮る。最終確認として1回撮り、Vision Criticの報告を記録する。差分があれば`MODIFY`ジョブの提案にする(承認が要る)。
- 静的なモデルで見えない部品(動くシャフトの回転、プレスの可動部など)は、`PREVIEW`では基本形の見た目になる。どの部品がどう見えるかは、スパイクS-4bで一覧にし、見えない部品には代替(下記S-4bの選択肢)を用意する。
- **カメラの一致の限界**: 画像生成AIは、指示した角度・距離・遠近を正確には守れない。したがってVision Criticは、**画素の類似ではなく、意味の比較**(屋根の形・色・数、建屋の相対位置、機械の並び)で差分を出す。比べる前に、両方の画像を、被写体の外接矩形でクロップして大きさを揃える。`matchScore`の閾値(0.75)は、人が判定した比較ペアの評価セット(S-10)で較正し、較正後の値で凍結する。

## L1: ユーザー → コンセプト洗練(絵へのダメ出しでプロンプトを直す)

| 項目 | 内容 |
|---|---|
| きっかけ | Approve0(N-04)で、ユーザーが「この絵ではない」と押す |
| 戻す先と中身 | Refiner(N-02)へ。ユーザーの言葉(「屋根をもっと大きく」)、却下した画像。Refinerが`ConceptBrief`を直し、`ImagePromptBuilder`が指示文を作り直す。必要なら却下画像を参考画像(否定例ではなく「ここを変える元」)に使う |
| 上限 | 1つのコンセプトにつき、画像の再生成**5回**。自動では回らない(毎回ユーザーが押す) |
| 終了条件 | ユーザーが承認する |
| 上限超過時 | `LoopEscalationScreen`(0.2節)。費用と回数を表示して「続ける/この絵で進む/中止」 |
| 費用 | 1回=画像生成1回(約2分。実測値を表示)。画像の回数の上限線も効く |
| 記録 | 却下理由と最終承認画像を`KnowledgeStore`(好み) |
| フェーズ | P8 |
| 完了の実測条件 | 実機で、ダメ出し→再生成→承認、が回る。承認画像が保存され、再生成のたびに`ImageArtifact`が増え、回数が保存される。5回で`LoopEscalationScreen`が出る |

## L2: Reconciler → コンセプトアート(絵が工程・床面積を収容できない)

**測れるものだけを測る**: 絵は透視投影で、ブロック単位の縮尺を持たない(`NormBox`は画像内の割合)。したがってReconcilerは、**絶対の面積ではなく、比率と数と種類**で判定する。実寸はSite Plannerが決める。

| 項目 | 内容 |
|---|---|
| コンセプトアートの様式 | **カットアウェイ(屋根を一部外して内部の機械が見える)の鳥瞰図**にする(`06` 5.5節)。建屋の外側だけでは、機械が写らず、機械の照合が測れないため |
| きっかけ | Reconciler(N-09)の決定論部分が、次のどれかを検出: (1)**建屋の数**が、必要な数(`CapacityReport`から、動力室・搬入出棟などの分割)より少ない。(2)**建屋の相対的な大きさの比**(`relativeFootprint`)が、必要な床面積の比から、許容(既定: 各建屋で±30%)を超えてずれる。(3)**見えている**(`visibility≠HIDDEN`)必須部品のうち、絵に描かれている割合(検出率)が閾値(既定0.7)未満。(4)**登録簿にない機械**(`unrecognized`のうち`prominent=true`)が、1つ以上。`HIDDEN`(屋根や壁で見えない可能性)の部品は、欠落として数えない |
| 戻す先と中身 | ConceptImg(N-03)へ。`ReconcileConstraints`(建屋ごとの最低の比、最低の建屋数、絵に描かれるべき部品、絵から消すべき登録簿外の機械)を、指示文の制約に入れて**再生成**する |
| **承認(v3のApprove0を迂回しない)** | 再生成は、**候補を最大2つ**自動で作り、Vision Reader+Reconcilerで評価し、**最も良い候補を、ユーザーに提示してApprove0で承認してもらう**。承認されるまで、次の段(Site Planner以降)へ進まない。以前の承認は、別の画像に対する物なので流用しない |
| 上限 | 自動の候補生成は**2回**(1回=最大2候補まで、合計の画像生成は2回)。それでも収容できなければユーザーへ |
| 終了条件 | 検出条件(1)〜(4)がすべて解消され、ユーザーが新しい絵を承認する |
| 上限超過時 | `LoopEscalationScreen`。「絵を優先して機械を減らす/工程を優先して建屋を大きくする(絵を再生成)/この絵で進む(不足は施工時に建屋を拡張、L4')」 |
| 費用 | 回るたびに画像生成(最も高い。1回ごとに費用表示、画像回数の上限線を厳守) |
| 記録 | 制約と結果を`KnowledgeStore`(失敗例) |
| フェーズ | P12 |
| 完了の実測条件 | 意図的に建屋が小さい・少ない絵で、L2が制約つきで再生成を要求し、新しい絵が**ユーザーの承認画面に出て**、承認されて通る。収容できる絵では発動しない。`HIDDEN`の部品は欠落と数えないことを確認 |

## L3: Capacity Calculator → Process Planner(動力不足・過大)

| 項目 | 内容 |
|---|---|
| きっかけ | `CapacityReport`に`E-POWER-NONE`/`E-STRESS-OVER`(動力不足。`PowerPolicy`の範囲内で動力源を選んでも足りない)、または`W-OVERSIZED-POWER`(過大。既定は必要量の3倍超) |
| 戻す先と中身 | Process Planner(N-06)へ。`Issue`(ID・不足量・`FixHint`)。**Process Plannerが変えられる物**(`01` 6節): 目標の毎分(`targetPerMin`)、レシピの選択、機械の組み合わせ(`setup`)、`PowerPolicy`(許す動力源・台数の上限)。Capacity Calculatorは、その範囲で動力源を選び直す |
| 上限 | **4回** |
| 終了条件 | `ERROR`が0件 |
| 上限超過時 | `LoopEscalationScreen`。生産量の目標を下げるか、動力源の種類を許すか、を返す |
| 費用 | Claudeの構造化出力1回/回(小さい) |
| フェーズ | P12 |
| 完了の実測条件 | 動力が足りない工程グラフ(水車のみ許可、目標が大きい)で`E-POWER-NONE`が出て、Process Plannerが目標を下げるか動力源の許可を広げて通る。過大な設定で警告が出る |

## L4: Factory Analyzer → Module Planner(ID付きエラー)

| 項目 | 内容 |
|---|---|
| きっかけ | `FactoryAnalyzer`(N-19)の`ERROR`: `E-ROT-CONFLICT`、`E-STRESS-OVER`、`E-PORT-UNCONNECTED`、`E-PORT-MISMATCH`、`E-NO-ROUTE`、`E-ITEM-DEADEND`、`E-CLOG-RISK`、`E-OVERLAP`、`E-HEAT-NONE`、`E-DOCK-MISALIGN`など(`E-SPACE-SHORT`はL4'へ) |
| 戻す先と中身 | Module Planner(N-16)へ。**対象のID(ノード・接続)と`FixHint`つきの`Issue`一覧**(番号ではなくID)。修正は`PlanPatch`で返させる |
| 上限 | **5回** |
| 終了条件 | 受け入れ不可の`ERROR`が0件。**かつ、`W-UNMODELED`の部品がある場合は、その部品を試運転(Commissioning)の検査項目に入れた状態**(モデルが無い部品を、解析だけで通さない。解析OKは「未検証の部品を含む」と表示し、施工後の試運転が通るまで`VERIFIED`にしない)。受け入れ可能な問題(例: `E-CLOG-RISK`)は、ユーザーが`ACCEPTED_RISK`にしたものだけ残せる |
| 上限超過時 | `LoopEscalationScreen`。残る`Issue`の一覧と、「レイアウトを手で直す(スクリプト編集)/前の段に戻る/中止」。**受け入れ不可の`ERROR`が残るときは「この構成で進む」を出さない** |
| 費用 | Claudeの構造化出力1回/回(中) |
| 記録 | 直した`Issue`と修正を`KnowledgeStore`(修正履歴) |
| フェーズ | P12 |
| 完了の実測条件 | 意図的に回転方向が衝突する配置で`E-ROT-CONFLICT`が出て、Module Plannerの修正で解消する。決定論の解析なので、同じ入力なら同じ`Issue`が出る(単体テスト)。上限に達したとき、受け入れ不可の`ERROR`が残ると、承認ボタンが無効のままで、「進む」が出ない |

## L4': Factory Analyzer → Architect(空間が足りない → 建屋拡張)

| 項目 | 内容 |
|---|---|
| きっかけ | `E-SPACE-SHORT`(スロットの不足、通路の不足、天井高の不足) |
| 戻す先と中身 | Architect(N-13)へ。`SpaceRequest`(建屋ID、必要な床面積・高さ・階) |
| 上限 | **2回** |
| 終了条件 | 空間不足が解消 |
| 波及 | 建屋が変わるので、`Invalidation`により、`SemanticMap`以降が「古い」になる。決定論の部分は即再計算、AIの段は資料が変わったものだけ再実行 |
| 上限超過時 | `LoopEscalationScreen`。「モジュールを減らす/敷地を広げる/前の段に戻る」(**空間不足の`ERROR`が残るなら「進む」は出さない**) |
| フェーズ | P12 |
| 完了の実測条件 | 狭すぎる建屋で発動し、建屋が広がり、下流が自動で再計算されて通る |

## L5: Vision Critic → Architect / Decorator(コンセプト画像と同じ角度のスクショと比較)

| 項目 | 内容 |
|---|---|
| きっかけ | Vision Critic(N-23)の`matchScore`が閾値(既定0.75。S-10で較正)未満 |
| 戻す先と中身 | 形・屋根・配置の差分(`SHAPE`/`ROOF`/`LAYOUT`)→ Architect。装飾の差分(`DECOR`/`COLOR`)→ Decorator。`Diff`(領域・種類・重大度・対象ID)。**`PREVIEW`撮影**で回す(世界は無変更、0.5節)。比較は意味の比較(0.5節) |
| 上限 | **3回** |
| 終了条件 | `matchScore`が閾値以上。または頭打ち(改善が0.03未満のまま2回)。頭打ちでもエラーではなく、ユーザーへ返す |
| 上限超過時 | `LoopEscalationScreen`。スコアの推移と差分の一覧を見せ、「続ける/この見た目で進む/絵の方を直す(L5')/中止」 |
| 費用 | 1回=Vision Criticの視覚呼び出し1回+修正のClaude呼び出し。画像生成は含まない(L5'を除く) |
| 記録 | 差分とスコアを`KnowledgeStore`(ダメ出し履歴)、`CritiqueRecord` |
| フェーズ | P9(建築)、P12(機械を含む工場) |
| 完了の実測条件 | 実機で、赤い屋根の指示を青い屋根で建てるプレビューに対し、屋根の差分が指摘され、修正でスコアが上がる。差が無ければ発動しない |

## L5': Vision Critic → DesignGen(物理的に実現不能 → スクショを元に絵を描き直す)

| 項目 | 内容 |
|---|---|
| きっかけ | Vision Criticの差分に`IMPOSSIBLE`(絵の形がブロックで表現できない、絵の機械が登録簿に無い等)がある |
| 戻す先と中身 | DesignGen(N-12)へ。**スクリーンショットを参考画像**として渡し、「この見た目をできるだけ保って、ブロックで実現可能な形に描き直す」。元の完成予想図も参考に(枠に収まる範囲、`06` 5.3節)。**描き直した絵は、ユーザーが承認する**(Approve0と同じ) |
| 上限 | **2回**(絵と実物を双方向に収束させる、v3の意図) |
| 終了条件 | 新しい絵でL5が通り、ユーザーが承認する |
| 上限超過時 | `LoopEscalationScreen`。「元の絵のまま、実現可能な範囲で進む/新しい絵を採用/中止」 |
| 費用 | 画像生成+その後のL5(高い。費用表示、画像回数の上限線) |
| フェーズ | P9(S-3で参考画像を渡す方式を確定した上で) |
| 完了の実測条件 | 実現不能な要素(例: 丸い屋根)を含む絵で発動し、描き直した絵がユーザーに提示・承認され、L5が通る |

## L6: Critique Router → 戻し先(雰囲気=Refiner / 生産量=Process Planner / 形・色=DesignGen / ラインの並び=Module Planner)

| 項目 | 内容 |
|---|---|
| きっかけ | Preview(N-24)で、ユーザーがダメ出しを入力 |
| 戻す先と中身 | Critique Router(N-25)が、ダメ出しを分類(`MOOD`/`PRODUCT`/`BUILDING_FORM`/`LINE_LAYOUT`/`OTHER`)して`RouteDecision`(戻し先と制約)を出す。戻し先の段が、制約つきでやり直す。世界の変更は`MODIFY`ジョブとしてもう一度承認 |
| 上限 | 自動の反復は無い(毎回ユーザーの入力)。**8回で止まる**: 8回目の後は、`LoopEscalationScreen`を出し、「続ける(+5回)/プロジェクトを整理して新しい版として保存/中止」から選ぶまで、次のダメ出しを受け付けない |
| 分類できないとき | `OTHER`→ユーザーに「どの部分ですか」と質問(選択肢: 雰囲気/生産/形・色/並び) |
| 記録 | ダメ出しと分類結果を`KnowledgeStore`(好み) |
| フェーズ | P14(戻し先のノードが全部揃ってから、1回で完成させる)。それまでは、ユーザーが`RouteChooserScreen`で戻し先を選んで手動で戻す |
| 完了の実測条件 | 4分類のダメ出し文(評価セット)が、正しい戻し先に振り分けられ、戻し先がやり直して`Invalidation`が正しく波及する。8回目で停止して画面が出る |

## L7: ワールド → ドローン(設置後のブロック状態を検査 → 失敗箇所の再施工)

| 項目 | 内容 |
|---|---|
| きっかけ | 施工の完了時(または一定ブロックごと)に、サーバーが**施工リストの配置位置だけ**を読み(`SparseSnapshot`)、`SnapshotDiff.compare(施工リスト, スナップショット)`が`Deviation`を返す |
| 戻す先と中身 | ドローン(`ConstructionJob`)へ。`RepairPlanner`が、`Deviation`だけを直す小さな施工リスト(`REPAIR`ジョブ)を作る。**AIは使わない**(厳密な差分で決まる) |
| 検査の内容 | ブロックの種類と、`VerifyMode`が求めるブロック状態(向き・軸・段・半分など)。向きの違う階段や扉も不合格になる。**`ASSEMBLED_AWAY`の配置は、「不在」が正常**で、組み立て後の`AssemblyExpectation`(エンティティ数・移動したブロック数)を検査する。組み立ては、置き直しの対象にしない(消えたブロックを欠落と誤判定しない) |
| 上限 | **3ラウンド** |
| 終了条件 | `Deviation`が0件(`VERIFIED`) |
| 上限超過時 | `PARTIAL`で終了し、残る`Deviation`の位置と理由(例: 置けないブロックが邪魔している、チャンクが読み込まれていない、材料不足)をユーザーに返す |
| 承認 | 不要(承認済みの施工リストの再適用のため) |
| フェーズ | P4(単純なブロック)、P10(風車の組み立て)、P13(飛行船の組み立て) |
| 完了の実測条件 | 実機で、施工後に意図的に壁のブロックを壊し・向きを変えると、検査が検出し、修復ジョブが直して`VERIFIED`になる。3回で直らない配置(例: 保護された邪魔なブロック)では`PARTIAL`になり、理由が出る。(P10)風車を組み立てた後に検査しても、帆が「欠落」と判定されず、期待どおりのエンティティが確認される |

## L8: Runtime Monitor → Module Planner(実測のボトルネック → 増設案)

| 項目 | 内容 |
|---|---|
| きっかけ | 試運転後の運転観測(`RuntimeReport`)で、計画値と実測値の差(既定: 目標の80%未満が5分以上続く)、停止、詰まり、過負荷、燃料切れを検出。**ユーザーが「観測」を有効にした時だけ**動く |
| 戻す先と中身 | **Module Planner(N-16)**へ(増設案を出すAIの段は、これだけ)。資料は`RuntimeReport`(ボトルネックの候補と順位)と現在の`SemanticPlan`。Module Plannerが増設案(`PlanPatch`の下書き)を出す |
| 上限 | セッションあたり**3回** |
| 終了条件 | ユーザーが増設案を承認して`MODIFY`ジョブが完了し、実測が改善する(0.1節のスコア)。または、ユーザーが却下 |
| 重要 | **稼働中の工場を自動では変更しない**。提案し、差分のホログラムを見せ、承認を得る(0.4節) |
| 上限超過時 | `LoopEscalationScreen` |
| 記録 | 実測と結果を`KnowledgeStore`(成功モジュール・失敗例) |
| フェーズ | P13 |
| 完了の実測条件 | 実機で、動力を意図的に不足させた工場で、停止・低速が検出され、動力の増設案が出る。承認で増設され、実測が改善する |

## L9: Knowledge Store → Module Library / Refiner(成功モジュール・好み・失敗例のセッション横断の蓄積)

| 項目 | 内容 |
|---|---|
| きっかけ | 終端イベント(施工が`VERIFIED`、試運転の成功、ユーザーの承認・却下、ダメ出し、修正の確定)。**記録の書き込みはP7から動く**(蓄積の受け口は最初から在る) |
| 中身 | `KnowledgeRecord`を保存(成功モジュール・修正履歴・ダメ出し履歴・好み・失敗例)。**新テンプレートへの昇格**: 候補が、(a)Factory Analyzerの静的検証を通り、(b)**そのプレイヤーの環境での試運転**に成功し(GameTestは使わない)、(c)ユーザーが「気に入った」と承認した場合だけ、`ModuleLibrary`に追加(`PromotionState=PROMOTED`、検証の由来=`PLAYER_COMMISSIONED`)。**好み・失敗例**は、タグの類似で決定論的に選び、Refinerの資料に少数(既定3件)入れる |
| 反復の上限と終了 | 反復ループではなく、**1つの終端イベントごとに、有限の作業(書き込み、昇順位の判定、選択)で終わる**。昇格の判定は、1イベントにつき1回だけ |
| 件数の上限 | プレイヤーごと既定1,000件。**90%に達したら、ユーザーに通知**。**100%に達したら、自動で消さず、`LoopEscalationScreen`で「古い物から整理(固定した物は残す)/書き出して整理/上限を上げる」から選ぶ**まで、新規の書き込みを保留する |
| プライバシー | 保存は利用者のPC内。共有はしない(利用者が明示的に書き出すまで) |
| フェーズ | 書き込み=P7、昇格・検索・整理=P14 |
| 完了の実測条件 | P7: 終端イベントの記録が保存される。P14: 成功した施工の後、テンプレート候補が昇格の条件を満たして登録され、次のプロジェクトのModule Plannerが選択肢として参照できる。過去の好みがRefinerの資料に入る。上限に達すると、自動で消さずに画面が出る |
